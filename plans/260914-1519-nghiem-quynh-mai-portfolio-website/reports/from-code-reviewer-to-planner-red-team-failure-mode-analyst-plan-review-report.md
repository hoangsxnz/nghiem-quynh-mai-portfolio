## Finding 1: Base-path fix for favicon/OG/canonical has no owning file
- **Severity:** Critical
- **Location:** Phase 1, section "Related Code Files" / step 8 (base-layout.astro); Phase 7, "Architecture" table + "Related Code Files → Modify"
- **Flaw:** Phase 7's Architecture table states "Every internal URL must go through `import.meta.env.BASE_URL`" (phase-07-responsive-a11y-qa-build-deploy.md:57) and calls the favicon/OG-image/canonical trio "the one real portability trap" (phase-07:61-63). But Phase 1 is where `src/layouts/base-layout.astro` is actually created, and its spec ("canonical from `Astro.site`, favicon, then fonts", phase-01-scaffold-tokens-fonts-data.md:190) never mentions `BASE_URL` prefixing. Phase 7's own "Related Code Files → Modify" list (phase-07:72-77: README.md, global.css, src/data/*.json, astro.config.mjs, .gitignore) does **not** include `src/layouts/base-layout.astro` — the only file where these three URLs live.
- **Failure scenario:** Phase 1 ships hardcoded `/favicon.svg`-style hrefs (or an `Astro.site`-only canonical with no base segment). Six phases later, Phase 7's QA step checks the three URLs, finds them broken under a project-page base (`/<repo>`), but has no file-ownership license (per its own Related Code Files list) to touch `base-layout.astro`. Either the fix silently happens off-plan (undocumented scope creep) or ships broken to GitHub Pages: 404 favicon, broken OG preview on social shares, wrong canonical (SEO self-harm, and Phase 7 requires Lighthouse SEO ≥ 90).
- **Evidence:** `phase-01-scaffold-tokens-fonts-data.md:190` ("canonical from `Astro.site`, favicon, then fonts") vs. `phase-07-responsive-a11y-qa-build-deploy.md:57` ("Every internal URL must go through `import.meta.env.BASE_URL`") vs. `phase-07-responsive-a11y-qa-build-deploy.md:72-77` (Modify list omits base-layout.astro).
- **Suggested fix:** Add explicit `BASE_URL`-prefixed href construction to Phase 1 step 8's base-layout.astro spec now, not as a Phase 7 discovery; add `src/layouts/base-layout.astro` to Phase 7's Modify list as a safety net.

## Finding 2: robots.txt is deployed under the project-page subpath, so it has zero effect on crawlers
- **Severity:** High
- **Location:** Phase 7, "Related Code Files → Create" and "Security Considerations"
- **Flaw:** Phase 7 creates `public/robots.txt` (phase-07:69) and treats it as the privacy control gate: "`robots.txt` allows indexing — confirm the owner wants the page indexed before the first deploy, since it carries personal contact details" (phase-07:242-244). But per the plan's own deploy table, the GitHub Pages project-repo target serves the site at `https://<user>.github.io/<repo>/` (phase-07:57). robots.txt is only honored by crawlers at the true domain root (`https://<user>.github.io/robots.txt`), which this repo does not own/control. A robots.txt shipped inside `/<repo>/robots.txt` is silently ignored by every compliant crawler.
- **Failure scenario:** Owner (or a cautious dev) sets `Disallow: /` in robots.txt believing it blocks indexing while placeholders/phone/email are still live, deploys to the GitHub Pages project-repo target, and the page gets crawled and indexed anyway — the phone number and email from `contact.json` become searchable, contradicting the exact risk the plan itself flags.
- **Evidence:** `phase-07-responsive-a11y-qa-build-deploy.md:57` (project-repo base `/<repo>`) + `phase-07-responsive-a11y-qa-build-deploy.md:242-244` (robots.txt treated as the indexing control).
- **Suggested fix:** For the GitHub Pages project-page target, note in the README that robots.txt has no effect and the only real controls are (a) not linking the URL publicly until ready, or (b) a `<meta name="robots" content="noindex">` tag (which *does* work per-page regardless of path) gated behind an env/build flag until placeholders are cleared.

## Finding 3: CSS reveal pre-state depends on a deferred script, risking an LCP flash on the hero
- **Severity:** Critical
- **Location:** Phase 6, "Architecture" (control-flow note) and "Implementation Steps" step 8/10 (CSS pre-state)
- **Flaw:** The reveal pre-state (`html.js [data-reveal] { opacity: 0 }`) only applies once JS adds the `.js` class, and that class is added by `motion/index.ts`, an ES module `<script>` at the end of `<body>` which the plan itself says runs "exactly once on `DOMContentLoaded`... Astro `<script>` is deferred by default, so the DOM is parsed when it runs" (phase-06-motion-layer-gsap-lenis.md:56-58). Deferred/module scripts execute only after the HTML parser finishes, by which point browsers routinely have already painted above-the-fold content — and the hero is explicitly the LCP element per Phase 7 ("hero is the LCP element and is not lazy," phase-07:30-31).
- **Failure scenario:** Hero paints fully visible (default opacity, no `.js` class yet) → script finally runs, flips `[data-reveal]` to `opacity:0` → reveal timeline animates it back to visible. This is a visible flash/pop on exactly the element the plan calls out for LCP sensitivity, and because the element is hidden then re-shown, Chrome's LCP candidate timing can land on the *second* (post-animation) paint rather than the first, directly threatening the Phase 7 gate "Lighthouse ≥ 90 on performance... desktop and mobile" (phase-07:217). The plan's own CLS-only test ("No cumulative layout shift... CLS contribution 0," phase-06:314) would not catch this since opacity/transform changes don't register as CLS — the regression would only show up as an LCP/performance-score drop, discovered late in Phase 7 with no assigned root-cause path back to this design.
- **Evidence:** `phase-06-motion-layer-gsap-lenis.md:56-58` (deferred-script timing) + `phase-06-motion-layer-gsap-lenis.md:68-80` (pre-state CSS + "this ordering is the single most important detail in the phase") + `phase-07-responsive-a11y-qa-build-deploy.md:30-31` (hero = LCP, eager).
- **Suggested fix:** Set the `.js` class synchronously via a tiny inline blocking script in `<head>` (not the deferred module), so the pre-state and the class land in the same paint — the classic anti-FOUC pattern — rather than relying on a deferred module script for a state that must exist before first paint.

- **Suggested fix:** Add the actual hero-timeline code block to step 4 (or step 5) so the two are consistent, and add a dedicated test-matrix row for "hero visible/animated on cold load with no scroll."

## Finding 5: `gsap.matchMedia()` re-runs the whole callback on any breakpoint cross, re-splitting headings and re-firing already-played reveals
- **Severity:** High
- **Location:** Phase 6, Implementation Step 8 (`index.ts`) and "Test Matrix" row 5
- **Flaw:** `mm.add({ motionOk, desktop }, ctx => { ...; initReveals(); initNavScroll(); if (ctx.conditions.desktop) initParallax(); ... })` (phase-06:254-266) re-executes the *entire* callback whenever **any** condition in the object changes state — not just `desktop`. `initReveals()` and `initNavScroll()` are unconditional inside that callback (only `initParallax()` is desktop-gated), so every time a user's viewport crosses the 768px breakpoint, `initReveals()` runs again. `splitWords()` (phase-06:150-169) destructively rewrites `el.textContent` into span markup — calling it a second time on the same heading re-splits already-split DOM. Any `[data-reveal]`/`[data-reveal-group]` already scrolled past and revealed gets a brand-new `ScrollTrigger` with `start: 'top 85%'`, which fires immediately on creation if the element is already above that threshold — replaying the reveal animation on content the user has already seen.
- **Failure scenario:** A user resizes a browser window (or rotates a foldable/tablet) back and forth across 768px after scrolling partway down the page. Already-revealed sections visibly re-animate (flash from `opacity:0` back to `1`), and repeated `splitWords` calls compound span nesting on headings. The plan's own Test Matrix row for this exact scenario, "Resize across 768 px | Drag window | No console error; parallax tweens reverted, no stuck transform" (phase-06:294), only checks parallax cleanup — it does not check reveal/ScrollTrigger duplication or repeated DOM splitting, so this regression would pass the plan's stated verification step while still being visibly broken.
- **Evidence:** `phase-06-motion-layer-gsap-lenis.md:254-266` (unconditional initReveals/initNavScroll inside matchMedia callback) + `phase-06-motion-layer-gsap-lenis.md:150-169` (destructive splitWords) + `phase-06-motion-layer-gsap-lenis.md:294` (resize test row scope).
- **Suggested fix:** Gate `initReveals()`/`initNavScroll()` re-execution with a run-once guard (e.g., a module-level boolean, or only calling them outside `mm.add` and putting only `initParallax` inside the conditional context), and extend the resize test row to check `document.querySelectorAll('[data-split] .word').length` stays constant and no already-visible `[data-reveal]` element re-animates.
