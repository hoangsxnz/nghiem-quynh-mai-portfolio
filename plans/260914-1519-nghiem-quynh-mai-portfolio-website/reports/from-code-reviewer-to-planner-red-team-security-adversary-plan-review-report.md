## Finding 1: Personal phone/email published with no scrape-resistance and no safe indexing default
- **Severity:** Critical
- **Location:** Phase 1, "Security Considerations" (`phase-01-scaffold-tokens-fonts-data.md:271`); Phase 3, `hero.json` `quickLinks` and `contact.json` `cards` (`phase-03-sections-hero-about-contact.md:90-93,181-182`); Phase 7, "Security Considerations" (`phase-07-responsive-a11y-qa-build-deploy.md:242-244`)
- **Flaw:** The plan emits `mailto:quynhmainghiem340@gmail.com` and `tel:+84368327616` as plain anchor text in two places (hero quick links, contact cards), and Phase 7 creates `public/robots.txt` with no specified `Disallow`, defaulting to indexable. The only mitigation is a README sentence telling the owner to "confirm... before deploy" — a soft, after-the-fact opt-out on a plan that already builds the exposed version by default.
- **Attack / failure scenario:** Any of the dozens of public GitHub-Pages/Vercel crawlers or a simple `grep -o 'mailto:[^"]*'` scraper harvests the address and number directly from static HTML with zero JS execution needed. Once indexed by Google (default `robots.txt` allows it per line 242), the phone/email pair is permanently searchable and paired with the owner's full name — a vector for targeted phishing/vishing and recruiter-spam scraping, and this is a personal phone/Gmail, not a company line.
- **Evidence:** `content-source.md:8` `**Phone:** 0368327616 · **Email:** quynhmainghiem340@gmail.com`; `phase-07-responsive-a11y-qa-build-deploy.md:242` `robots.txt allows indexing — confirm the owner wants the page indexed before the first deploy, since it carries personal contact details.`
- **Suggested fix:** Ship `robots.txt` with a real default the plan actually specifies (either `Disallow: /` until the owner explicitly flips it, or keep indexable but make it an explicit go/no-go gate before Phase 7 is marked done, not a README footnote). For contact links, note a cheap mitigation such as building `href` at build-time via a small obfuscation helper (reversed string / char-code join) instead of literal `mailto:`/`tel:` text in source — doesn't need JS to render, cuts down naive scrapers.

## Finding 2: Case-study/chart screenshots become permanently exposed in git history once pushed, regardless of later "disclaimer" placeholder
- **Severity:** High
- **Location:** Phase 4, `strategy.json.caseStudy.disclaimer` (`phase-04-sections-branding-strategy-seo.md:172,277`); Phase 1 image move step (`phase-01-scaffold-tokens-fonts-data.md:123`)
- **Flaw:** `chart-views-gained.png` and `chart-subscribers-gained.png` (screenshots of a former employer's channel analytics) are moved into `src/assets/images/` and committed in Phase 1, before the owner has confirmed permission to publish them. The plan's only safeguard is a `[PLACEHOLDER: xác nhận với chủ sở hữu kênh...]` string that renders a "cần bổ sung" sticker on the live page — it does not gate whether the image file itself gets committed or built.
- **Attack / failure scenario:** The repo is a public GitHub Pages source repo (implied by Phase 7's GitHub Pages workflow). The moment it's first pushed, the chart images are in the object history. If the channel owner later refuses permission, deleting the JSON reference or even the file does not remove it from git history — anyone with `git clone` + `git log --all` still recovers the "confidential" growth numbers of a third party's business.
- **Evidence:** `phase-04-sections-branding-strategy-seo.md:172` `"disclaimer": "[PLACEHOLDER: xác nhận với chủ sở hữu kênh trước khi công bố số liệu và ảnh chụp màn hình]"`; risk table row at `phase-04-sections-branding-strategy-seo.md:277` only says the placeholder "renders on-page until the owner clears it" — no statement about gating the commit itself.
- **Suggested fix:** Treat the disclaimer as a pre-commit gate, not a post-hoc render gate: don't add the chart PNGs to the initial commit (or don't push the repo publicly) until the channel owner's permission is confirmed in writing. Add this as an explicit Phase-1 or pre-deploy checklist item, not just a Phase-4 UI sticker.

## Finding 3: Google Fonts CSS2 request leaks every visitor's IP to Google with no self-hosting or notice
- **Severity:** Medium
- **Location:** Phase 1, step 8 (`phase-01-scaffold-tokens-fonts-data.md:190-196`); risk table (`phase-01-scaffold-tokens-fonts-data.md:266`)
- **Flaw:** `base-layout.astro` loads fonts directly from `fonts.googleapis.com`/`fonts.gstatic.com` on every page view. The plan's own risk table acknowledges self-hosting via `@fontsource` as the safer alternative but explicitly defers it: "stays a documented fallback, not built now."
- **Attack / failure scenario:** Not an exploit, but a passive data-exposure: every visitor's IP address, user-agent, and referrer are sent to Google on page load without the visitor's consent or any privacy notice. For a Vietnamese personal portfolio this is a soft compliance/reputational risk (Vietnam's Decree 13/2023 on personal data protection covers this class of processing) and a known point of legal exposure if any EU visitor's data is in scope (the 2022 Munich Google-Fonts ruling made this a real liability class for exactly this pattern).
- **Evidence:** `phase-01-scaffold-tokens-fonts-data.md:193-195` `<link rel="stylesheet" href="https://fonts.googleapis.com/css2?family=Be+Vietnam+Pro...` ; `phase-01-scaffold-tokens-fonts-data.md:266` `Self-hosting via @fontsource stays a documented fallback, not built now`.
- **Suggested fix:** Self-host via `@fontsource-variable/be-vietnam-pro` and `@fontsource/protest-guerrilla` from the start — same visual result, zero third-party request, and the plan already names the package family as the fallback, so this is a same-effort swap, not new scope.

## Finding 4: GitHub Actions pinned by mutable tag; `withastro/action@v3` is three major versions stale
- **Severity:** Medium
- **Location:** Phase 7, step 9 workflow (`phase-07-responsive-a11y-qa-build-deploy.md:166-193`)
- **Flaw:** All three actions (`actions/checkout@v4`, `withastro/action@v3`, `actions/deploy-pages@v4`) are pinned to floating major-version tags, not commit SHAs. Confirmed live against GitHub: `withastro/action`'s latest release is `v6.1.2` — the plan pins to `v3.0.x`, three major versions behind, meaning roughly three years of fixes (including whatever Node/Astro compatibility and security patches landed since) are skipped.
- **Attack / failure scenario:** Tag-based pinning (vs. SHA-pinning) is a known supply-chain weakness: a floating tag can be repointed by the action's maintainer (or an attacker who compromises the action repo) to different code without the consuming workflow's `@v3` reference changing — the workflow silently runs whatever `v3` resolves to at trigger time. This exact class of attack (mutable tag repoint) was used in the March 2025 `tj-actions/changed-files` supply-chain compromise.
- **Evidence:** `phase-07-responsive-a11y-qa-build-deploy.md:180` `uses: withastro/action@v3`; live check via GitHub API confirms current tags run through `v6.1.2` (`v6.1.2, v6.1.1, v6.1.0, v6.0.0, v6, v5.2.0, ... v4, v3.0.2, v3.0.1, v3.0.0, v3, ...`).
- **Suggested fix:** Pin all three actions to a commit SHA with a version comment (`uses: withastro/action@<sha> # v6.1.2`), and bump `withastro/action` to current `v6` — the `v3` reference is not just a supply-chain smell, it's stale enough that the plan should re-verify it still supports the pinned Node 22 / Astro 7.3 combination before relying on it.

## Finding 5: Dev-only `/ui-kit` page is shipped to production by default
- **Severity:** Low
- **Location:** Phase 2, step 10 (`phase-02-shared-components.md:122`); Phase 7, README section (`phase-07-responsive-a11y-qa-build-deploy.md:164`)
- **Flaw:** `/ui-kit` is built with `noindex` and left unlinked, but the plan explicitly defers the keep-vs-delete decision to Phase 7 documentation rather than defaulting to excluded from the production build. `noindex` only suppresses search-engine indexing — it does not prevent direct access; the page is still emitted into `dist/` and served at a guessable, static path on GitHub Pages/Vercel with no authentication.
- **Attack / failure scenario:** Low impact here since it only exposes internal component styling, not data — but it's a real instance of a dev/test surface reaching production by default, which is exactly the pattern that in other projects leaks internal tooling, staging banners, or debug info. Worth calling out because the plan's own security section (Phase 2, line 162) claims "No `set:html` anywhere in `ui/`" as the safety net, but doesn't address whether the page ships at all.
- **Evidence:** `phase-02-shared-components.md:122` `Phase 7 decides keep-hidden vs delete and records the decision in the README.`
- **Suggested fix:** Default to excluding `ui-kit.astro` from the production build (e.g., gate it behind an env var checked at build time, or simply delete it as the last step of Phase 2/7) rather than making retention the default state that requires an active decision to undo.
